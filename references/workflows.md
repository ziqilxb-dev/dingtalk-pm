# PM协作与信息整理

以需求挖掘、评审、变更核对和交付推进为优先场景。客户、运营、客服及研发讨论作为产品协作来源；用户明确要求其他协作任务时也可使用。根据问题选来源、核对事实并交付，不要求先选择岗位；纯信息整理不运行PM初始化。

| 任务 | 读取与判断 | 交付 |
|---|---|---|
| 需求评审与变更核对 | 评审原话、后续沟通与当前PRD逐项比较 | 已确认变更、冲突、漏改点及建议修改位置；附依据 |
| 项目进展回顾 | 指定主题的讨论、会议和任务，核对后续更新 | 已完成、在推进、阻塞、待决定；活动不等于成果 |
| 客户/销售跟进 | 指定客户的可访问沟通、会议、材料 | 诉求、已作承诺、待回复、下一步；不推断成交或自动发送 |
| 运营/客服/采购问题复盘 | 指定事件/订单的沟通、记录、文档 | 时间线、已知影响、处理状态、未解问题；不把猜测当根因 |
| 会前准备 | 对应日程、上次会议、相关待办/资料 | 本次目标、上次结论、未完成事项、待决策点 |
| 会后整理 | 纪要或转写，必要时核对相关文档 | 决定、分歧、待确认和真实行动项；缺负责人/日期不补造 |
| 研发/测试协作 | 需求或技术评审、变更、缺陷及发布材料 | 变更影响、未决问题、风险和验收关注点；讨论完成不等于开发完成 |
| 日报/周报 | 用户指定范围的事实来源 | 同一项目合并，区分准备、推进、完成，不凑数量；未经验证的进度留限定 |
| 文档核对 | 当前文档与后续确认资料 | 原文、变更依据、建议修改与待确认；明确要求写回才写入 |
| 台账/任务维护 | 当前记录与新增证据 | 先识别已有项避免重复；确认目标与用户要求后执行增改并读回 |

## 多平台合并

只读取本次所需来源。区分“接口没有此能力”“未授权”“权限不足”“范围内无数据”“尚未核验”。一个平台失败时继续其余来源，但不以另一平台相似标题替代缺失原文。跨平台人员、客户和项目关联依赖真实名称及上下文证据，有歧义就保留分开。

读取失败时不默认要求用户复制全部材料，先完成可访问部分并指出最小缺口。只总结时直接回答，不强制保存文件。

## 可选移交格式

需要下游继续处理才生成work-handoff.json，保留：

- source_packets：平台、来源类型、原始响应路径、查询范围、分页完成状态及剩余缺口。
- items：业务事项、分类（fact/decision/proposal/question/conflict/action）、结论、证据引用和限制。
- evidence：平台、标题、日期、链接及真实对象/段落定位；跨平台ID不混用。
- proposed_actions：目标、建议操作、依据及状态，未实际执行只能为draft。
- performed_actions：仅记录用户已授权并实际执行的变更、返回值和读回结果。

产品任务转入pm-workflow.md和pm-handoff.md，复用同一证据，不为岗位重新采集无关数据。
